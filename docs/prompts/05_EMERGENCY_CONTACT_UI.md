# Prompt 5 — Emergency and sticky contact UI

Copy everything below into a new development task and fill in the bracketed inputs.

> Improve the emergency and contact conversion UI for [REPOSITORY], [DOMAIN], and assigned pages [SCOPE]. First inspect the current Temporary123 preview and `src/Site.tsx`, `src/contact-refresh.css`, contact interactions, `QuoteForm`, site configuration, and existing tests. Temporary123 currently has a header `Call our team, 24/7` action; an emergency trigger `24/7 support / Call now` that expands to `Need equipment urgently?`, a phone CTA and `Check urgent availability`; and a left contact rail `Need a rental? / Contact now` that opens a `Request availability` dialog. These are functional reference points, not instructions to duplicate their exact colors, placement, or wording on every site.
>
> Give the emergency action and contact action clearly different jobs. Emergency should emphasize a verified phone path for time-critical rentals; general contact should collect equipment, location, timing, and project details without implying instant service. Design a distinctive, polished interface appropriate to [SITE BRAND] and [EQUIPMENT FAMILY]. The two floating elements must not overlap each other, the main content, cookie notices, map controls, or mobile navigation. Avoid oversized boxes, rotated/illegible labels, aggressive motion, and multiple simultaneous popups. Make each control's purpose readable at a glance on desktop and mobile.
>
> Recommend and test concise CTA wording against the actual service. Suitable candidates: `Need equipment urgently? Call 24/7`, `Request rental availability`, and `Speak with the rental team`. Use `Live agent` only if live staffing and response are verified. Keep the number, operating hours, discounts, inventory, and arrival claims truthful and centrally configured. The emergency call must use a real `tel:` link. The availability path must reach the working contact flow; never present a disabled form as accepting requests or show a fake success state. Explain that availability and delivery timing require team confirmation.
>
> Make the sticky contact entry intentionally interactive: clear hover/focus state, compact collapsed state, accessible expanded drawer, useful project fields, and a visible call alternative. If the owner approves a timed emergency prompt, show it only after meaningful browsing and at most once per session, respect dismissal, never block essential content, and suppress it while the contact dialog is open. Otherwise keep emergency user-initiated. Do not introduce a timed popup by default merely because the original request mentioned one.
>
> Implement proper dialog behavior: keyboard open/close, Escape, focus entry and return, correct labels and expanded state, scroll handling, reduced-motion support, sufficient contrast, touch targets, and no horizontal overflow. Verify mobile portrait, tablet, and desktop on representative homepage, service, and location pages. Test that call links dial the configured number, the contact CTA opens the intended form or page, form submission uses the existing secured flow, errors preserve input, and success is shown only after confirmed downstream acceptance. If backend delivery cannot be verified, state that boundary explicitly.
>
> Preserve existing URLs, H1s, canonicals, indexability, and the site navigation. Deliver a before/after preview, exact CTA copy, interaction-state checklist, accessibility and responsive evidence, and any unverified operational assumptions. Coordinate shared files with other developers. Do not commit, push, or deploy before assigned review and approval of the target environment.
